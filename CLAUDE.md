# About voice-intake

## What it owns

`127.0.0.1:8332` (`VOICE_INTAKE_ADDR`, loopback by default). Speech from the phone in, agent sessions out: the phone posts an utterance (one press of a trigger) and then each segment of speech as it ends, and this service sends the text into llm-bridge-server sessions created **as the signed-in person**, so each request is a real conversation in that person's chat, and streams the sessions' events back. It owns the utterances, segments, the one session each utterance's segments went to and the later messages sent into it, the decisions and their reasons, the addressee checks, the pool of waiting sessions, and the timings. It owns no session: llm-bridge-server does. SQLite at `voice-intake.db` in `VOICE_INTAKE_DATA_DIR`, ids `utterance_000001`. **The phone-facing API is a fixed contract** that an Android app is built against: README "Routes" and "Events" are the contract as served, and README "Contract changes" lists every addition. Do not change a route, field or event the phone reads; add, and write the addition there.

## Where this prompt lives

These sections are stored in agent-store as a project prompt collection and rendered, with identical text, to `AGENTS.md` and `CLAUDE.md` at the root of this repo, so that whichever file a harness reads it gets the same thing. Edit them on dash `/files`, or edit either rendered file: the 15-minute scan carries the edit back into the sections and out to the other file. The host prompt keeps one row for this repo with only what an agent elsewhere needs.

# How it works

## Dispatch and decisions

`dispatcher.go`. **One press, one session.** Each utterance has one `utteranceRun` whose worker handles segments **one at a time, in index order**. The first segment with words goes to a pooled session when one is ready and the text runs at the default effort, else to a new one (`dispatch`), and is decided `kept` at once; it is `run.conversation`. Every later segment with words goes into that session as its next message (`sendIntoConversation`, event `follow_up`, a row of `session_follow_ups`): the session has every earlier word, so it judges what the new ones mean, and nothing here does. A turn still running is interrupted first (`InterruptSession`), and three things keep the interrupted turn's closing `result` from being taken for the reply, which the live bridge would otherwise allow (measured 2026-11-25: the bridge echoes the new message at once, the old turn's empty `result` comes 50 to 80 ms later, stamped with the **new** turn's `turn_id`): `discarding` drops everything while `awaitInterruptedTurnEnd` waits for that result before the new message is sent; `awaitingOwnMessage` with `awaitedText` then drops events until the new message's own echo; and `interruptedMessageIDs` drops any block or result of the old turn that comes later still. Never tell turns apart by `turn_id`. `streamSession` reads a session for as long as the utterance lives, across turns. **Replies wait while the person speaks** (`replyHeldBack`, `releaseHeldReplies`): for a streamed recording, session events are kept in `heldEvents` from the detector hearing speech until that speech's segment is handled; more words drop a running turn's draft, and pass a finished turn's reply on first. `finalize` runs on finish, or, for segments the phone cuts itself, when the window passes (`scheduleWindowExpiry`); **a streamed recording becomes final only after its stop**, and `checkDone` never sends `done` while a stream is open, because `done` closes the event hub and a later `stop_recording` would be dropped (it happened on 2026-11-17). `checkDone` sends `done` once the utterance is final, no held words wait, and the session has its `result` (or five minutes pass, `sessionTurnLimit`). The event hub (`event_hub.go`) keeps the whole history, so a late subscriber misses nothing. README "How segments are dispatched" says the same for a reader outside the code: keep the two in step. Until 2026-11-25 a later segment started two more sessions and a continuation judge chose between them; `continuation_judgments` is that history and nothing writes it. An utterance's `target` (`target.go`) changes this: `new_session` dispatches as above but starts its session with `CreateChatSession` (the chat's instance and defaults, purpose `chat`) instead of the pool; `session` and `signal` send nothing segment by segment: `spokenTexts` holds every segment with words and `deliverToTarget` sends them joined, once, at `Finish`, to the person's session or through `POST /signals/{id}/answer`. Those sessions are `ownedByVoiceIntake: false`, so `stopSession` only stops following them, and `awaitingOwnMessage` holds back their events until the `user_message` this send made, because the bridge first replays the session's last turn to a new subscriber. By default `session`, `signal` and `new_session` utterances also **hold** the joined words at finish (`collectsOneMessage`, `holdForConfirmation`): `awaiting_confirmation` goes out, nothing is final, and `ConfirmHeldWords` (route `/confirm`), `Cancel` or the two-minute `expireConfirmation` ends it; `Store.ResolveConfirmation` is the one atomic step that decides which of the three won. README "Targets" and "Confirmation" are the reader's version.

## The addressee check

`addressee_check.go` and `checkAddressee`. Beside the session, never ahead of it, a model reads the words so far (`POST /oneshot` on `addressee_check_model_role`, schema `for_assistant` and `reason`) and each answer is a row of `addressee_checks`. One check runs at a time; words that arrive meanwhile set `addresseeCheckStale` and it runs again on all of them — never cancel a running check for a newer one, or a conversation that never pauses long enough is never judged. Typed words, replays, held words and the person's own session are not checked. **Not for the assistant** (`withholdAsNotForAssistant`): the session's turn is interrupted and `withheld` drops its events, a live stream gets `stop_recording` `not_for_assistant`, and once every word is in (`Finish`) `holdForConfirmation` holds them with `confirmation_reason` `not_for_assistant` and sends `not_for_assistant`, **not** `awaiting_confirmation`, because the phone sends held words by a countdown. Confirm sends the words again, whole, into the same session (`sendWithheldWords`); cancel and expiry stop and archive it. **The check failing** is an `error` event and holds nothing. It runs beside the session because one such model call takes 3 to 5 seconds here, as long as the session's first words: measure before moving it ahead. README "The addressee check" is the reader's version.

## The pool, and the prompt voice sessions read

`session_pool.go` keeps `pool_size` started sessions per person, each matching the default effort, model, instance and working directory; it fills a person's pool at their first utterance and, at start, for everyone with one. `Take` asks the bridge for the session's state and gives up one that is `aborted`, `error`, `disconnected` or `completed`. A session the bridge's idle reaper stopped reads `completed`, and the bridge cannot resume it: it never had a turn, so Claude Code saved no conversation for it. A settings change runs `Resync`, which gives up the sessions that no longer match. **Voice sessions get their prompt from the session working directory**, not from `append_system_prompt` or `system_prompt` in `harness_config`, which would override the context the bridge injects: `VOICE_INTAKE_SESSION_WORKING_DIR` is the root of a project prompt collection in agent-store, and Claude Code reads its rendered `CLAUDE.md` because the session starts there. That directory and its collection are host setup, not part of this repo; the noteboard note tagged `voice-intake` names them. Sessions are `interactive`, purpose `voice`, origin `voice-intake`; llm-bridge's purpose registry does not list `voice` yet, so the bridge logs a taxonomy notice per create.

## Timings

Every time column is server epoch milliseconds. A phone timestamp is stored as sent (`*_client_ms`) and plus the skew of its own request (server time at receipt minus `X-Client-Now-Ms`). Per session: dispatch started, dispatched, first `block`, `result`, stopped, and whether it was pooled with the pooled session's state at the moment it was taken; these describe the session's first message, and each later message has its own sent, first `block` and `result` times in `session_follow_ups`. An audio segment (`POST …/segments/{index}/audio`, transcribed in `transcription.go` by the service the `transcriber` setting names in `VOICE_INTAKE_TRANSCRIBERS`) also records when transcription started and ended, its WAV size and length, and the raw transcript; one with no words is stored with empty text, holds its index and dispatches nothing, and a failed transcription stores nothing. `GET /api/voice/latency?group_by=strategy|pooled|trigger|source` takes medians per group in Go (`latency.go`), each interval measured from the speech end of the last segment the session's first message holds. This table is how strategies and pooled-versus-fresh are compared: never drop a timing column, and add one rather than reuse one.

## Streaming, speech-server and replays

`streaming.go` takes contract v2's streamed PCM: each chunk is scored by speech-server's Silero detector (`speech_detection.go`, `VOICE_INTAKE_SPEECH_DETECTION_URL`), the endpointer ends a segment after `endpoint_silence_ms` of silence and drops speech under 200 ms, and the segment is cut with 200 ms padding, transcribed and handed to the dispatcher with source `stream`. Every stop condition is measured in audio time, so a replay decides as the live stream did: `maximum_recording_ms`, `no_speech_timeout_ms`, the continuation window since the last segment, and `maximum_quick_segments` segments cut (`segment_limit`). A segment too weakly heard to transcribe counts as no speech for all of them. Two guards run in real time and only for a live phone: `stopRecordingGrace` ends a stream the phone did not stop within 10 seconds of `stop_recording`, and `streamIdleLimit` ends one that sent no audio for 20 seconds (`stopFromThisSide`); without them nothing would finish such an utterance. `speech-server/` is a separate Go module (cgo over whisper.cpp's libparakeet and libwhisper) that keeps Parakeet and the VAD in memory; `deploy.sh` builds and restarts it, with cgo flags from a host-local build file (README "Host setup"). `replay.go` runs stored recordings or texts under named configurations (detector, silence, transcriber, dispatch, instance, model, effort, working directory, warm session, budget) and `GET /api/voice/latency?group_by=configuration` compares them: **choose settings from that table, not from a script.** Replay sessions are created as the caller, run with `max_budget_usd`, and are stopped and archived after their turn. Recordings for replay are private: they live in the data directory (`replay-recordings/`), never in the repo. The noteboard note tagged `voice-intake` names this host's recordings, configurations and results.

# Access and operations

## Who may call it

Every `/api/voice/` route takes requests only from loopback and needs `X-Principal-Id` (403 off loopback, 401 without it; `requireKnownPrincipalFromLoopback`). The id must be an enabled principal in principal-store (`VOICE_INTAKE_PRINCIPAL_STORE_URL`, `principal_check.go`): an unknown or disabled one is 403, principal-store not answering is 502, and a confirmed one is believed for a minute. The pool fills at start only for people principal-store confirms, so a test's made-up id is never retried. dash is the front door: it proxies `/api/voice/` unchanged and sets `X-Principal-Id` from the signed-in caller after deleting any the browser sent. An utterance of another principal is 404. `GET /health` and `GET /settings` are open on loopback. `/admin/app/releases` (publish and list the phone app's builds, `app_releases.go`) takes loopback plus `X-Voice-Intake-Publish-Token` matching `VOICE_INTAKE_APP_RELEASE_PUBLISH_TOKEN` (host drop-in; the token's copy for publishers is in auth-store); dash does not proxy `/admin/`. The APKs lie in `app-releases/` in the data directory. This service calls llm-bridge-server with its service token (`LLMBRIDGE_SERVICE_TOKEN`) and, when creating a session, `X-Principal-Id` naming the person; it calls model-store only to check a new addressee-check role or default model, and principal-store to check each principal.

## Unit, settings and deploy

User unit `voice-intake.service`, `%h/bin/voice-intake`. The committed unit sets only the address; the service token, `VOICE_INTAKE_INSTANCE_ID`, `VOICE_INTAKE_SESSION_WORKING_DIR`, `VOICE_INTAKE_TRANSCRIBERS`, `VOICE_INTAKE_TRANSCRIBER` and `VOICE_INTAKE_SPEECH_DETECTION_URL` come from a host-local drop-in, `voice-intake.service.d/host.conf`, never from a tracked file. Every variable is declared once in `settings.go`; the contract settings and the ones added since are editable, stored in the database after the first start, and changed only through `PATCH /api/voice/settings`, which checks the addressee-check role and a model with model-store and an instance with llm-bridge-server before writing anything. Deploy only with `./deploy.sh` from the main clone on `main`: it runs `~/bin/deploy-gate check`, the tests, the live-environment check, installs and restarts, smoke-checks the routes and the loopback bind, and records the deploy.

# Working in this repo

## Tests

`go test -race ./...`. `dispatcher_test.go` drives the HTTP API against `fakeBridge` (a sent message produces a `user_message`, a `block` and then a `result`; an interrupt ends the running turn with a `result` of its own) and `fakeAddresseeJudge` (for the assistant unless the words hold one of its phrases): a later segment goes into the same session as its next message, with both turns' results passed on and the follow-up recorded; a later segment interrupts a turn still running, and that turn's result is never passed on; words not meant for the assistant are withheld, never sent as `awaiting_confirmation`, and their session is stopped and archived when nobody sends them; sent anyway, they go again into the same session and are not checked twice; a failed check is an `error` and holds nothing; segments the phone cuts stop at the limit; `trigger_detail` is stored; a repeated segment index and a repeated `client_utterance_id` change nothing; cancel stops the session; the window passing finalizes without `finish`; an effort-raising phrase skips the pool. `streaming_test.go` streams made-up PCM (loud samples are speech to `fakeDetector`) and checks hearing, transcript and stop_recording events, two pauses making two segments, a 64 ms tick making none, long mode as one segment, offsets and stop reasons, word accuracy, a replay end to end, a reply kept back while the person speaks and its turn interrupted by more words, the stop at the limit of segments, weak noise neither keeping the window open nor counting as speech, `done` waiting for the recording to stop, and a stream ended from this side when the phone does not stop or its audio stops arriving. `segment_audio_test.go` posts segment audio to a fake whisper-server that reads the transcript out of the WAV's sample bytes: audio is dispatched like text, a silent segment holds its index and does not block the window, a failed transcription leaves the index free, and a WAV not 16 kHz mono PCM is refused. `target_test.go` covers targets: a malformed target is 400; a session target gets one joined message after finish, passes on only the new reply (not the turn the bridge replays) and is never stopped, not even by cancel; a signal target answers every open question of its group; `new_session` starts a chat session, not a pooled one; a streamed reply across two pauses is one message. A live end-to-end run creates real sessions in the person's chat: stop and archive every one you create.
